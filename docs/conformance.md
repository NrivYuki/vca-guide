# 規格との対応表

DCS v3.14 の各節が、このリポジトリのどこで扱われているかの一覧です。データの読み書き(レコード・データセット・パケット)は [src/vca-parser.js](../src/vca-parser.js)、通信の制御(確認応答・タイムアウト・再送・セッションの手順)は [src/vca-session.js](../src/vca-session.js)、TCP・UDP での接続は [src/vca-tcp.js](../src/vca-tcp.js) が受け持ちます。

各行をどのテストが確かめているか(件数と、正常・異常・境界・規格の例のどれか)は、[conformance-tests.md](conformance-tests.md) にあります。テストには確かめる行を書いてあり(`test(名前, { spec: [行], kind: [確かめ方] }, …)`)、`tools/trace.js` がこの表と突き合わせて作ります。GitHub Actions は、◎ の行に正常系と異常系(または境界値)の両方のテストがあること、U の行に異常系のテストがあること、行の書き間違いが無いこと、一覧が古くないことを確かめます(例外は[異常系を求めない行](#異常系を求めない行))。

この表は節の単位です。節の中の義務・推奨・ほかの言い方の義務を文ごとに分けた一覧は [requirements.md](requirements.md) にあります。

状態の記号は次のとおりです。

| 記号 | 意味 |
|---|---|
| ◎ | 実装があり、テスト([tests/tests.js](../tests/tests.js)・[tests/session-tests.js](../tests/session-tests.js)・[tests/tcp-tests.js](../tests/tcp-tests.js))がある |
| △ | 一部だけ実装している(何が無いかは備考) |
| 解説 | ライブラリでは扱わず、README・docs で解説している |
| - | 扱っていない |

「実装」の欄は関数名です(`createDevice`・`createHost` などは vca-session.js、`connectDevice` などは vca-tcp.js、ほかは vca-parser.js)。「解説」の欄の章番号は README の章です。

## 規格に書かれていない場面の扱い

規格書は、通信が乱れたときの扱いをすべては書いていません。次の場面は、このリポジトリで扱いを決め、テストで確かめています([tests/session-tests.js](../tests/session-tests.js))。

| 番号 | 場面 | 起こり方 | 扱い | 根拠 |
|---|---|---|---|---|
| U1 | 同じパケットがもう一度届く | こちらの ACK がノイズで NAK に化け、相手が規格どおり送り直した | ACK を返して捨てる(2 回処理しない)。相手から ACK・NAK を受け取ったら「相手は先へ進んだ」とみなし、次に同じ内容が来ても新しいパケットとして受け取る | 再送の仕組み(6.1.3.1)から正当に起こるため、同期ずれにはしない。前のセッションと同じ要求(`REQ=TIM` を 2 回など)は区別できる |
| U2 | 確認応答より先に相手のパケットが届く | ACK が遅れた、または化けて届かなかった | パケットには ACK を返して取り置く。あとで ACK が来れば、取り置いたパケットを次のパケットとして受け取る。NAK が来るか確認応答が来ないままなら、同期ずれ | 相手がこちらのパケットを受け取ったかどうかは、確認応答が来るまで分からないため |
| U3 | 同期ずれ | 上の NAK・確認応答なしの場合、応答の種類(`ANS`)が要求と違う場合、アップロードのデータの代わりに別の要求が届いた場合 | `STATUS=12` のパケットを送り、セッションを中止する。相手から `STATUS=12` が届いたら、確認応答だけ返して中止する(送り返さない)。両側が同時に `STATUS=12` を送っても繰り返さない | 表 A.24 の 12(Out of sync): 同期のずれたパケットを受け取ったら、そのパケットに確認応答を返し、この番号を出して、両側とも中止する |
| U4 | データセットの途中に `REM` がある | DCS Host Simulator は、`R` レコードの間にも `REM` を入れて送ってくる | データセットを閉じずに、`REM` を通常のレコードとして記録する | `REM` は「どのパケットに現れてもよい」(表 A.2)とされ、データセットの途中を禁じる記述は無い |
| U5 | `REM` の値に引用符の無い `;` がある | DCS Host Simulator は `REM=STATUS=0;   "NO ERROR"` のように送ってくる | 分けずに 1 つの文として記録する | `;` は本来使えない(5.1.8.1)が、`REM` は処理に使わない備考なので、分けて警告を出すより 1 つにまとめるほうが実用的 |
| U6 | 断りの応答に `JOB` が無い | DCS Host Simulator は、知らない要求種別や `CMD` に `JOB` を付けずに `STATUS=18` を返す | `STATUS` が 0 以外なら、結果に番号と説明文を入れて受け取る(`jobMissing` を付ける)。`STATUS=0` なのに `JOB` が無ければ失敗 | 7.1.6 には合わないが、断りの理由を失わないため。成功の応答は、どのジョブのデータか分からないので受け取らない |
| U7 | 確認応答を待つ間・パケットを待つ間に切断された | 相手の電源が切れた、ケーブルが抜けたなど | タイムアウトを待たずに、すぐ `closed` で失敗させる。タイマーも止め、あとでタイムアウトとして二度失敗しない | 切断が分かった時点で呼び出し側に知らせるほうが、原因を取り違えない |
| U8 | パケットが長すぎる | 終わりの `GS` が届かない、または壊れたデータが続く | 受信中のパケットが上限(既定 1 MiB、`maxPacket` で変更)を超えたら読み捨てて `too-large` で知らせ、`GS` が来たら NAK を返す | 規格にパケットの長さの上限は無い。面形状の表(141 × 141 の値など)でも数百 KB なので、メモリを使い続けないための安全上限として決めた |
| U9 | `GS` で終わらないまま次の `FS` が来た | `GS` が失われた | 前のパケットを捨てて、新しいパケットとして読み直す(再同期) | バイナリの中の `FS` はエスケープされる(5.4.16)ので、エスケープされていない `FS` は必ずパケットの始まり |
| U10 | オートコネクトの知らせ(`REQ=CON`)の中身がおかしい | 壊れた知らせ、または第三者のアドレスへ誘導する知らせ | `IP` が IP アドレスの形でない、`PORT` が 1-65535 でない、`IP` が UDP の送り主と違う、`allow` で断った、すでにつないでいる、のどれかならつながない(理由は `onIgnore` で知らせる) | 7.8.2.7.1 ではデバイスは自分の IP を知らせる。UDP の知らせをきっかけに、意図しない相手へつながないため |
| U11 | 確認応答が ACK でも NAK でもない | 通信速度などの設定が合っていない | タイムアウトを待たずに中止する(`bad-confirmation`) | 6.1.3.1 の注記(このとき操作者に「Unrecognized confirmation」のような表示をするとよい) |

## 独立した実装との照合(DCS Host Simulator)

The Vision Council の DCS Host Simulator(ホスト役のソフト。応答では `OMAV=3.07` と名乗る)に、`createDevice` で TCP でつないで確かめました。手順は [tools/sim-check.js](../tools/sim-check.js) です。Simulator は各自で入手する必要があり(配布はできない)、Windows の画面を持つソフトなので GitHub Actions では動かせません。やり取りの記録には Simulator の試験用のジョブが入るため、リポジトリには入れていません。

Simulator は、デバイスを試すために規格の範囲でわざと崩したデータを送ります(行末を CRLF・LF・CR・LFCR・CRCR・LFLF からランダムに選ぶ、ラベルや区切りの前後に空白を入れる、どこにでも `REM` を入れる)。同じダウンロードを 5 回繰り返し、どれも正しく読めることを確かめました。

| 場面 | 結果 |
|---|---|
| 初期化(自動フォーマット・プリセット、CRC あり・なし) | 3.14 の 7.2.2 の手順どおりに進み、要求 ID と形式の取り決め(`TRCFMT=1;400`、`4;400`)を受け取れた |
| 要求 ID でのダウンロード | 左右 400 点ずつの玉型(形式 1)を読めた |
| 要求に `TRCFMT=4` を入れたダウンロード | 形式 4 の玉型を左右 400 点ずつ復号でき、Simulator が送った `HBOX`・`VBOX` と一致した |
| ないジョブ | `STATUS=1`(ジョブが見つからない)を受け取れた |
| `TIM`・`INF`・`TRC` のアップロード | 規格の手順どおりに終わった |
| 知らない要求種別(`XYZ`)・`CMD` | `JOB` の無い `STATUS=18` が返る。`createDevice` はこれを断りの応答として受け取る(上の表) |

**照合から対応したこと**:データセットの途中の `REM`、引用符の中の `;`、引用符の無い `;` を含む `REM`、`JOB` の無い断りの応答の 4 つです(上の表。それぞれテストがある)。

**Simulator のくせ(このリポジトリでは合わせていないもの)**

- 知らない要求種別と `CMD` に `STATUS=18`(書式エラー)を返す。表 A.24 では 16 が当たり、本文 7.6.2 は 8 とする([下記](#対応しない要求種別に返す状態コード8-と-16))
- 規格のどの版(3.02-3.14)にも無いラベル `SGERIN`・`SGERUP` を送る。パーサーは知らないラベルとして扱う(5.1.5)
- 同じパケットに `FPINB` を 2 回入れる。パーサーは重複の警告を出す
- 要求で 400 点の形式 4 を求めると、`CIRC` が送った玉型から計算した値と 0.2 mm ほどずれる(元の 800 点の値のまま送っていると考えられる)。`checkSizing` が検出する
- 初期化せずに `EDG` を要求し、要求に `TRCFMT` を入れないと、玉型を送らない
- 試験用のジョブの 1 つ(両眼で同じ玉型のもの)は、玉型のデータの `TRCFMT` の眼に `B` を使う。規格 5.4.12.3 は、`B` を要求・初期化にだけ使い、データでは眼ごとに分けるとしているので、パーサーは警告を出す。玉型は読み、両眼の玉型として扱う(Simulator のジョブのファイルで確認。Simulator との通信では確認していない)

**確かめられないこと**:Simulator はホスト役だけなので、`createHost` は照合できません。また 3.02-3.07 の時代の実装なので、3.14 で増えた機能(測定値の接頭辞のレコード、`ENGMARK` の欄など)は試せません。

## 規格書の中の食い違い

DCS v3.14 の規格書には、本文と表、または本文どうしで食い違う箇所があります。このリポジトリでは、規格書のほかの箇所(本文・表・例)とより多く合うほうを正しいと考えて合わせ、どちらに合わせたかと理由をここにまとめています。理由の多くは推測で、規格書に書かれているわけではありません。

| 箇所 | 規格書の記述 | このリポジトリでの扱い | 理由 |
|---|---|---|---|
| 7.6.2・7.7.2 と表 A.24 | 対応しない要求種別(`CMD`・`LNF`)に `STATUS=8` を返す | **`STATUS=16` を返す(本文と違う)** | [下記](#対応しない要求種別に返す状態コード8-と-16) |
| 7.1 ほか | 知らない要求種別(`REQ=XYZ`)に返す値の指定が無い | `STATUS=16` を返す | [下記](#知らない要求種別に返す状態コード) |

| 表 A.1 の説明文 | `CTHK`・`CKPRHI`・`CKPRVI`・`CKTHK` は、説明文でだけ廃止(後継あり)とされ、廃止の印が無い | 廃止として扱う(後継: `CTHICK`・`CKPRVHI`・`CKPRVVI`・`CKCTHICK`) | 説明文に後継のラベルが明記されている |

### 対応しない要求種別に返す状態コード(8 と 16)

- **規格書の記述**:7.6.2 は、コマンドのセッションに対応しないホストは `STATUS=8` を返すとし、例では `STATUS=8;unrecognized request type` としています。7.7.2 も、LNF を扱えないホストは `STATUS=8, Invalid Request Type` を返すだろうと書いています
- **食い違い**:表 A.24 では、8 は「ホストの内部エラー(Host error)」です。「ホストが要求の種類を特定できない(Invalid request)」に当たるのは 16 です
- **このリポジトリの扱い**:番号の意味を定めた表 A.24 に合わせて **16** を返します。**本文の指定とは違います**
- **理由**:
  - 表の 8 と 16 の意味は、手に入った最も古い 3.02(2001 年)から 3.14 まで変わっていない
  - `CMD`・`LNF` の節は 3.08 か 3.09 で加わった(3.07 には無く、3.09 にある)。本文が 8 に付けた説明「Invalid Request Type」は、表の 16 の名前とほぼ同じ
  - このため、本文の 8 は 16 の誤記と考えた。規格書に理由の記載は無く、推測です
- **8 を返すとき**:表どおり「ホストの内部エラー」の意味でだけ使います(応答を作る関数が例外を投げたとき)
- **本文どおりにしたいとき**:`createHost({ statusCodes: { unsupportedRequest: 8 } })` で 8 に変えられます
- **受け取る側の注意**:本文に従って 8 を返すホストもありえます。`createDevice` は 0 以外の `STATUS` を番号によらず失敗として扱い、説明文(`statusText`)も返します

### 知らない要求種別に返す状態コード

- **規格書の記述**:表 A.3 にも 7.5.1 にも無い要求種別(`REQ=XYZ` など)に何を返すか、本文には指定がありません
- **このリポジトリの扱い**:表 A.24 の 16 の定義(ホストが要求の種類を特定できない)に合わせて **16** を返します
- **ほかの実装**:The Vision Council の DCS Host Simulator は `REQ=XYZ` に `STATUS=18`(書式エラー)を返します。合わせたいときは `createHost({ statusCodes: { unknownRequest: 18 } })` とします
