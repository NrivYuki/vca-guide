# VCA通信(OMA / DCS)入門: 眼鏡店・ラボの機器と PC のデータ通信を日本語で

眼鏡店やレンズ加工ラボで「VCA通信」「VCAフォーマット」と呼ばれている、トレーサーや加工機(エッジャー)などの機器と PC の間でデータをやり取りするための規格を、実装する人向けに日本語で解説します。

あわせて、この規格のデータを読み書きできる JavaScript のライブラリと、自作のサンプルファイルを置いています。

> 前提とした版: The Vision Council Data Communication Standard v3.14(2025 年公開)
> この記事は規格書の翻訳ではなく、規格を読んだうえで要点を独自にまとめたものです。正確な定義は必ず[公式の規格書](#12-参考資料)で確認してください。

## 1. VCA通信とは

同じ規格がいくつもの名前で呼ばれています。

| 呼び方 | 由来 |
|---|---|
| VCA | 規格を管理する団体の旧名 Vision Council of America(2008 年に The Vision Council へ改称)。日本では「VCA通信」「VCAフォーマット」がよく使われる |
| OMA | さらに前の団体名 Optical Manufacturers Association(1999 年に統合されて VCA に)。英語圏ではこの呼び方が主流で、ファイル拡張子も `.oma` が多い |
| DCS | 正式名 Data Communication Standard の略 |
| OMAV | 規格のバージョンを表すレコード名(例: `OMAV=3.14`) |

英語で情報を探すときは「VCA」より「OMA」で検索したほうが見つかります(`OMA file format`、`OMA TRCFMT` など)。日本語で「OMA ファイル」と検索するとソニーの音声形式(同じ拡張子)が出てくるので注意してください。

### 国際規格・JIS との関係

- かつては ISO 16284 と ANSI Z80.24 としても出版されていました。v3.14 の前書きによると、どちらも取り下げられ、現在は The Vision Council の DCS が唯一の規格とされています。
- 日本の JIS T 7335:2005(眼鏡レンズ製造システム間の情報交換)は ISO 16284:2001 を基にしています。基本的な仕組みは同じですが、内容は 2000 年代前半のものです。

### 版の履歴

ネットで手に入る最も古い 3.02(2001 年)から最新の 3.14(2025 年)までの旧版を比べ、版ごとの変更とラベルの追加を [docs/history.md](docs/history.md) にまとめています。

## 2. 登場する機器と役割

規格では、通信の両端を次のように呼びます。

- ホスト(host): 受注データや加工データを持つコンピュータ。ラボ管理システム(LMS)や店舗の PC。
- デバイス(device): 実際に作業する機械。トレーサー、加工機、カーブジェネレーター、ブロッカー、レンズメーターなど。

最も大事な原則は「セッションは必ずデバイスから始める」ことです。ホストのほうから要求を出すことはありません。デバイスが「このジョブのデータをください」「測定したデータを送ります」と要求し、ホストが応じます。

ただし TCP/IP では、接続そのものはホストからデバイスの待ち受けポートへ張ることがあります([接続方式](#ネットワークtcpip))。接続をどちらが張るかと、セッションをどちらが始めるかは別で、接続した後に最初のパケットを送るのはやはりデバイスです。

デバイスが何をしたいのかは、要求パケットの `REQ` レコードの値で表します。主なものは次のとおりです。

| 値 | 意味 | 方向 |
|---|---|---|
| `INI` | 初期化(機器の自己紹介と取り決め) | 双方向 |
| `TRC` | トレーサーからの玉型送信 | アップロード(デバイス→ホスト) |
| `EDG` | 加工機(エッジャー)へのデータ要求 | ダウンロード(ホスト→デバイス) |
| `GEN` | カーブジェネレーターへのデータ要求 | ダウンロード |
| `SBK` / `FBK` | ブロッカー(表面加工用/加工機用) | ダウンロード |
| `LMD` | レンズメーター | ダウンロード |
| `INS` | 検査機器からの測定結果 | アップロード |
| `INF` | 作業完了の通知 | アップロード |
| `UPL` / `DNL` | 汎用のアップロード/ダウンロード | アップロード/ダウンロード |
| `TIM` | 時刻合わせ(`JOB` なし) | ダウンロード |
| `FIL` | ファイルとして保存したデータ | 通信なし |

このほかの種別(穴あけ機の `DRL`、コマンドの `CMD`、保守情報の `MNT` など)は規格書の表 A.3 にあります。

## 3. 接続方式

### シリアル(RS-232C)

もともとの接続方式です。既定値は 9600 bps・データ 8 ビット・ストップ 1 ビット・パリティなしです。フロー制御を使う場合は RS-232C の制御線で行い、XON/XOFF(ソフトウェア制御)は使いません。

### ネットワーク(TCP/IP)

v3.04 から規定されています。通信の中身(セッション)はシリアルと全く同じで、通り道が TCP になるだけです。

| ポート | 用途 |
|---|---|
| 50000(既定) | デバイスが待ち受けるポート。ホストがここへ接続する(ローカル接続) |
| 33511 | オートコネクト用。デバイスが起動時に UDP ブロードキャストで「自分の IP とポート」を知らせる |
| 33512 | ホストが待ち受けるポート。デバイスから接続する(リモート接続) |

TCP で接続してから最初のセッションを始めるまで、デバイスは 3 秒待つ決まりです。後述の CRC は接続方式にかかわらず省略できます(TCP 自体にも誤り検出があります)。

### ファイル

通信せずにファイルでやり取りする方法もあります(3.02 には無く、3.07 にはある。間の版は手に入らないため、どの版で加わったかは分かりません)。中身は後述のパケットとほぼ同じで、次の点だけが違います。

- パケットの開始・終了などの制御文字、`CRC`、`STATUS` は入れない
- 1 行目は `REQ=FIL`(リムレスのフレームデータは `REQ=FRM`、面形状定義ファイルは `REQ=SDF`)、ジョブのデータなら 2 行目は `JOB=...`
- 玉型データは形式 1(ASCII)のみ

「VCA ファイル」「OMA ファイル」と呼ばれるものの多くはこの形式です(機器やソフトによっては独自の拡張があります)。[samples/](samples/) に例があります。

## 4. レコードの書き方

データは 1 行 1 項目の「レコード」の集まりです。

```
ラベル=値1;値2
```

- ラベルと値の区切りは `=`、値どうしの区切りは `;`
- 左右(chiral)レコードは「右眼の値;左眼の値」の順

  ```
  SPH=-2.25;-2.50     右 -2.25、左 -2.50
  SPH=;-2.50          左眼だけの注文
  DBL=18.0            左右の区別がない項目は値 1 つ
  ```

- 左右レコードなのに値が 1 つしかない場合は、両眼に同じ値を使う(受け取る側はこれを許容する)
- 値が不明なときは `?` を入れる(例: `IPD=?;31.0`)
- 1 つの値の中に複数の数値を入れるときは `|` で区切る(`TOLVADD=-0.04|0.06;-0.04|0.06` のような min|max など。使えるのは規格の表で決められたレコードだけ)
- ラベルは最大 16 文字。`_` で始まるラベルは機器メーカーの試験用
- 1 つの値は最大 255 文字(v3.13 から。それ以前は 80 文字)。limited 型(`JOB` など)は 12 文字まで
- 知らないラベルは無視する(エラーにしない)
- 文字は ASCII の 32-127(`;` を除く)。文字列の欄だけは、取り決めれば UTF-8 も使える(`TXTENC` レコード。初期化で、初期化しない場合はセッションごとに取り決める)
- v3.03 より前は文字列を `"` で囲むことがあったので、受け取る側は引用符を外せるようにしておく

### 数値の決まり

- 長さは mm、角度は度、屈折力はディオプター
- カーブ(`FRNT`・`BACK` など)は `TIND` で指定された屈折率で換算したディオプター(既定は 1.53)。素材の屈折率 `LIND` とは別物です
- 凸面は正、凹面は負の値で表します

## 5. パケットの構造

通信では、レコードを「パケット」にまとめて送ります。制御文字を `<FS>` のように表記すると、形は次のとおりです。

```
<FS>REQ=TRC<CR><LF>
JOB=A0001<CR><LF>
DEV=TRC<CR><LF>
<RS>CRC=12345<CR><LF>
<GS>
```

(`CRC=12345` の値は説明用の仮の数字です)

| 文字 | コード | 役割 |
|---|---|---|
| FS | 0x1C | パケットの開始 |
| GS | 0x1D | パケットの終了 |
| RS | 0x1E | CRC レコードの直前に置く(CRC が無ければ GS の直前) |
| CR LF | 0x0D 0x0A | レコードの区切り |
| ACK | 0x06 | 受信成功の返事 |
| NAK | 0x15 | 受信失敗の返事 |
| ESC | 0x1B | バイナリデータ中のエスケープ |

順序の決まりは 3 つだけです。

1. 最初のレコードは `REQ`(要求)または `ANS`(応答)
2. 初期化以外では、2 番目は必ず `JOB`(ジョブ番号)。ホストは受け取った形式のまま返す
3. `CRC` を付けるなら最後(`RS` の直後)。`CRC` が無くても `RS` は `GS` の直前に置く

2 の例外として、時刻合わせ(`TIM`)、保守情報(`MNT`)、ネットワークの自動接続(`CON`)には `JOB` がありません。レンズ情報の要求(`LNF`)は 2 番目が `OPC`、コマンド(`CMD`)は `JOB` の代わりに `LIB` か `RMT` でもかまいません。

`REQ` の無いパケットを受け取ったホストは、`ANS=ERR` と `STATUS=18` を返します。

### CRC

`CRC` は省略できます。付ける場合は CCITT CRC-16(多項式 0x1021、初期値 0。XMODEM と同じ計算)で、FS の次の文字から RS までの全文字を対象に計算し、10 進数で書きます。相手が CRC を付けてきたら、こちらも付けて返すのが推奨です。

```js
// 確認用: "Hello World!" の CRC は 0x0CD3
function crc16(str) {
  let crc = 0;
  for (const ch of str) {
    crc ^= (ch.charCodeAt(0) & 0xff) << 8;
    for (let b = 0; b < 8; b++) crc = crc & 0x8000 ? ((crc << 1) ^ 0x1021) & 0xffff : (crc << 1) & 0xffff;
  }
  return crc;
}
```

## 6. 確認応答とタイムアウト

パケットを受け取った側は、1 文字の ACK か NAK を必ず返します。

- NAK を受けたら同じパケットを送り直す。再送は 3 回まで(合計 4 回 NAK なら中止して操作者にエラー表示)
- 決められた時間内に返事が来なければ、再送せずにセッションを中止します

| タイムアウト | 既定 | 内容 |
|---|---|---|
| 確認応答 | 6 秒 | パケット送信後、ACK/NAK が来るまで |
| パケット | 12 秒 | ACK を受けてから、相手のパケットが届き始めるまで |
| 文字間 | 5 秒 | パケット受信中、次の文字が来るまで |

この値は初期化時に `TIMEOUT` レコードで変更できます(2-255 秒)。

## 7. セッションの流れ

1 つのジョブについての一連のやり取りを「セッション」と呼びます。セッションは途中で別のセッションと混ざることはなく、必ず 1 つずつ完結させます。

### アップロード(例: トレーサーが玉型を送る)

```
デバイス                         ホスト
<FS>REQ=TRC / JOB=A0001 <GS>  →
                              ←  <ACK>
                              ←  <FS>ANS=TRC / JOB=A0001 / STATUS=0 <GS>
<ACK>                         →
<FS>ANS=TRC / JOB=A0001 /
  TRCFMT=... / R=... <GS>     →
                              ←  <ACK>
                              ←  <FS>ANS=TRC / JOB=A0001 / STATUS=0 <GS>
<ACK>                         →
```

ホストが返す `STATUS` が 0 以外なら、そこでセッションは失敗です。

### ダウンロード(例: 加工機がデータをもらう)

```
デバイス                         ホスト
<FS>REQ=EDG / JOB=A0001 <GS>  →
                              ←  <ACK>
                              ←  <FS>ANS=EDG / JOB=A0001 / STATUS=0 /
                                   (加工に必要なレコード一式)<GS>
<ACK>                         →
```

### 初期化(INI)

電源投入時などに、デバイスが自分の情報(メーカー `VEN`、機種 `MODEL`、種別 `DEV` など)や、対応できる玉型形式(`TRCFMT`)をホストに伝えるセッションです。必須ではありませんが、強く推奨されています。

- 流れ: デバイスの `REQ=INI` → ホストの応答(`STATUS=0` なら自動フォーマットとプリセットのどちらでもよい、`14` ならプリセットのみ、`15` なら初期化に非対応)→ デバイスのデータパケット(`DEV`・`VEN`・`MODEL`、対応できる `TRCFMT` など)→ ホストのデータパケット(要求 ID と、使う `TRCFMT` を 1 つ)。ホストは少なくとも `STATUS=15` を返せなければなりません
- 自動フォーマット初期化: デバイスが「今後このレコード一式を送ってほしい」というリストを `DEF`・`D`・`ENDDEF` レコードで送ります。ホストはそのリストに要求 ID(整数)を割り当てて `DEF=タグ;要求ID` で返し、以後デバイスは `REQ=要求ID` で要求します。
- プリセット初期化(`DEF` を送らない): 規格が決めた種別ごとのレコード一式(プリセットパケット、表 A.5-A.23)を使います。v3.04 から、データを受け取る機器では廃止扱いで、トレーサーのように送るだけの機器で使います。
- ホストが再起動して要求 ID を忘れた場合などは、ホストが `STATUS=5`(初期化が必要)を返し、デバイスは初期化をやり直します。
- 初期化しない機器は `REQ=EDG` のような決まった種別で要求し、`TRCFMT` などの取り決めも要求パケットに入れます(開発・試験・小規模向けの簡易モード)。

### 主なステータスコード

| コード | 意味 |
|---|---|
| 0 | 正常 |
| 1 | ジョブが見つからない |
| 3 | 一般エラー(内容は説明欄) |
| 4 | この機器向けには処理できないジョブ |
| 5 | 初期化が必要 |
| 7 | 必要なレコードが不足 |
| 8 | ホストの内部エラー(本文 7.6.2・7.7.2 は、対応しない要求種別にもこの番号を使うと書いている。10 章を参照) |
| 10 | 値が範囲外 |
| 14 / 15 | 自動フォーマット初期化に非対応/初期化に非対応 |
| 16 | 要求の種類が分からない(Invalid request) |
| 17 | 非対応の玉型形式(256・512・1024 を足して、形式・点数・角度モードのどれが合わないかを示すことがある) |
| 18 | 書式エラー(規格どおりに解析できない) |

すべてのコードは規格書の表 A.24 にあります。`src/vca-parser.js` の `STATUS` にも日本語の要約を入れています。

## 8. 玉型(トレース)データ

フレームの形は、中心からの半径を角度ごとに並べたデータで表します。

### TRCFMT レコード

玉型データは必ず `TRCFMT` から始まり、直後に半径の `R` レコードが続きます。

```
TRCFMT=形式;点数;角度モード;眼;対象
```

| 項目 | 値 |
|---|---|
| 形式 | `0` データなし(この場合は項目 1 つだけ)/`1` ASCII/`2` バイナリ絶対値/`3` バイナリ差分/`4` パックトバイナリ(5-100 は将来の予約)。すべての機器とホストは形式 1 に対応しなければならない |
| 点数 | 半径の個数(400 や 512 など) |
| 角度モード | `E` 等角度/`U` 不等角度(`A` レコードで角度を送る)/`C` 自由(角度が戻ってもよい。v3.09 以降) |
| 眼 | `R` 右/`L` 左(初期化と要求では `B` 両眼も可) |
| 対象 | `F` フレーム/`P` 型板/`D` デモレンズ |

両眼分を送るときは、右眼と左眼それぞれに `TRCFMT` を付けます。

### 半径と角度

- 形式 1 の半径は 1/100 mm 単位の 4 桁の整数。例: `2479` は 24.79 mm
- 1 行は 80 文字以内なので、`R=` が何行にも分かれます
- 角度(`A`)も 1/100 度単位の整数で、0-35999
- 立体形状(サグ)は `ZFMT` と `Z`・`ZA` で同様に送ります。サグを扱えないホストは `ZFMT=0` を返す
- 玉型と同じ書式のデータセットに、削り落とし形状(`CRIBFMT`)、面の厚み(`STHKFMT`)、棚(`SHLFFMT`)があります([docs/records.md](docs/records.md#データセット))

```
TRCFMT=1;360;E;R;F
R=2457;2473;2490;2506;2522;2538;2553;2568;2582;2597;2612;2627;2642;2657;2672
R=...
```

([samples/frame-right.vca](samples/frame-right.vca) の冒頭。0° の半径は 24.57 mm)

### 向きの決まり

- 最初の点は 0°(時計の 3 時の方向)で、反時計回りに並べる
- 検者が装用者を正面から見た向きで表す。このため、右眼のデータは鼻側から、左眼のデータは耳側から始まる
- 右眼用のデータを左眼に使うときは、左右反転(角度 θ → 180° - θ)する
- 半径の基準は玉型の幾何中心(ホストが意図的にずらす場合は `FBFCIN`・`FBFCUP` でずれ量を示す)
- `HBOX`(横幅)、`VBOX`(縦幅)、`CIRC`(周長)は、送った半径データの形と一致していなければならない

### バイナリ形式(形式 2・3・4)

- 形式 2: 半径 1 つを 16 ビット整数(下位バイトが先)で表す
- 形式 3: 最初の半径は 16 ビット、以降は前の値との差を符号付き 1 バイトで表す。差が大きすぎるときは `0x80` を置き、続く 2 バイトを絶対値とする
- 形式 4: 16 ビット・8 ビット・4 ビットの 3 種類を切り替えて詰め込む、最も効率のよい形式(規格書の附属書 B に完全な例あり)。値の個数(`TRCFMT` の点数)が分からないと復号できない
- バイナリ中に予約制御文字(FS・GS・RS・CR・LF・ACK・NAK・ESC など)と同じ値のバイトが出たら、ESC を前に置き、そのバイトの最上位ビットを立てて送る(例: 0x0A → 0x1B 0x8A)。受け取る側は逆の処理をする
- CRC はエスケープ後のデータで計算する

## 9. 実装の手順

玉型データを受け取って使うまでの流れです。

1. 受信: FS から GS までをためる。文字間 5 秒を超えたら中止
2. 確認応答: CRC があれば検証し、ACK か NAK を返す
3. 分解: CR/LF で行に分け、`ラベル=値` を取り出す。知らないラベルは読み飛ばす
4. トレースの復元: `TRCFMT` の形式に従って半径(と角度)を取り出す。バイナリ形式ならエスケープを戻してから復号する
5. 座標に変換: i 番目の点の角度は、等角度なら `i × 360 / 点数`。半径 r と角度から x = r cos θ、y = r sin θ。角度は度で与えられるので、プログラムの三角関数に渡すときはラジアン(θ × π / 180)に直す
6. 眼の向きを合わせる: 必要なら左右反転

このリポジトリの [src/vca-parser.js](src/vca-parser.js) を使うと、3-6 は次のように書けます。

```js
const data = VCA.parse(fileText);                 // ファイル内容(1 文字 = 1 バイト)
const trace = data.traces.find(t => t.eye === 'R') || data.traces[0];
const points = VCA.tracePoints(trace, 'R');       // 右眼の向きの座標列(mm)
const { hbox, vbox } = VCA.boxOf(points);         // 横幅・縦幅
const ipdRight = VCA.number(data, 'IPD', 'R');      // 左右の別は定義表に従う
```

ファイルを読むときは、バイナリ形式が壊れないよう UTF-8 として解釈せず、1 バイト = 1 文字で読み込んでください(ブラウザなら `file.arrayBuffer()` → `VCA.bytesToString()`)。

### 位置に関するレコード

玉型データが表すのは、箱の中心を基準にした形だけです。眼の位置との関係は、次のような別のレコードで送られます。

- `MPD`: フレーム PD。左右の `HBOX` の平均に `DBL` を足した値(ホストが補正を加えることもある)
- `IPD`: 片眼の中心間距離(いわゆる片眼 PD)
- `OCHT`: 箱の下端から測ったプリズム基準点(PRP)の高さ。光学中心の高さではない点に注意

## 10. つまずきやすい点

- データが来ない: 初期化に応答していない、ACK を返していない、通信速度などの設定が違う、のどれかが多い原因です
- 機種によってはバイナリ形式で送ってくる: 初期化で対応形式を伝えるか、機器側の設定で形式 1 に変える
- `U` と `C` の違い: `U` は角度が順に増える、`C` は角度が戻ってもよい(鍵穴のような形)。`C` は等角度データに変換できない
- 左右の値の扱い: 値が 1 つなら両眼、空欄や `?` は「不明」
- カーブの符号: 凸面は正、凹面は負。眼鏡レンズの後面は通常凹面なので、`BACK` は負の値になる
- `TIND` と `LIND`: カーブは `TIND`(既定 1.53)基準、素材の屈折率は `LIND`
- `DBL` は左右の区別がない: 値は 1 つ
- 引用符: 古い機器は文字列を `"` で囲んで送ってくることがある
- `JOB` の無いパケット: `TIM`・`MNT`・`CON` などは 2 番目が `JOB` でなくて正常(5 章)
- 穴あけデータ: `DRILLE` は先に `DRLFMT` で基準(箱中心・縁・外接箱)を取り決めてから使う。古い `DRILL` は廃止([docs/records.md](docs/records.md#穴あけdrille))
- 規格書の誤植: 表 A.1 の `HBO` は `HBOX` のこと(本文・プリセット表・例はすべて `HBOX`)。表 A.16 の `INSSGUP` は、同じ表の `TOLSGOCUP` と対になる `INSSGOCUP` のこと
- 状態コードの食い違い: 対応しない要求種別(`CMD`・`LNF`)に返す値を、本文 7.6.2・7.7.2 は `STATUS=8` とするが、表 A.24 では 8 は「ホストの内部エラー」で、「要求の種類が分からない」は 16。相手のホストがどちらを返すかは実装による。知らない要求種別(`REQ=XYZ`)に返す値は本文に指定が無く、DCS Host Simulator は 18 を返す
- 規格書の中の食い違いと、このリポジトリでの扱いは [docs/conformance.md](docs/conformance.md#規格書の中の食い違い) にまとめています

### vca-parser.js でできること

データの読み書き(レコード・データセット・パケット)を受け持ちます。通信の制御は次節の vca-session.js です。規格の節ごとの対応は [docs/conformance.md](docs/conformance.md) にまとめています。

- レコードの解析(左右の値、`?`、引用符、`_` ラベル、`|` 区切りに対応)。データ型の要件(文字の範囲、limited は 12 文字まで、値は 255 文字まで)に合わない値は警告する。ほかにも規格の義務に合わないデータを警告する(左右のレコードの値の数、`LTYPE` の書き方、`XSTATUS` と `STATUS` の組み合わせ、`PROCBLK` のブロックの連続、`DRILLS` の欠かせない欄、機器の状態の `MNT` に要るレコードなど。一覧は [docs/requirements.md](docs/requirements.md))
- 附属書 A の全ラベル(表 A.1・A.1a・A.2・A.27、約 500 個)の定義表による判別: 左右か単一か、複数回出現してよいか、廃止されたか(後継ラベル)。測定値の接頭辞(`INS`・`TOL`・`TOLV`・`CK`・`LD`)付きのラベルも判別する
- 値の取り出し: `value()`・`number()`(左右の別は定義表に従う)、`fieldsOf()`・`occurrences()`(`DRILLE`・`XSTATUS`・`ENGMARK` などは欄に名前を付けて返す)
- データセットの復元: 玉型(`TRCFMT`・`ZFMT`)、削り落とし形状(`CRIBFMT`)、面の厚み(`STHKFMT`)、棚(`SHLFFMT`)は形式 1・2・3・4、角度モード E・U・C に対応。面形状(`SURFMT`・`PASSFMT`)、度数分布(`PMFMT`)、重み(`WMFMT`)、設計誤差(`DDFMT`)の表も読む
- 形式 4(パックトバイナリ)の符号化と復号。規格 5.4.15.4 の例とバイト単位で一致することをテストで確認
- 穴あけデータ(`DRILLE`、廃止された `DRILL`)の解釈: 基準(箱中心・縁・外接箱)、穴・長穴・矩形、角度モードの省略時の扱い、グループ、左眼への反転(`drillFeatures()`・`mirrorFeature()`)。逆向きに、穴の一覧から `DRILLE` レコードを組み立てる(`drillRecords()`。穴が無いときは `DRILLE=0`)
- 装置ごとのレコード(`PROC`、`PROCBLK` と `1!LABEL=` 形式のブロック)の取り出し(`deviceRecords()`)
- 初期化: 自動フォーマット定義(`DEF`・`D`・`ENDDEF`)の取り出し、初期化・要求パケットの `TRCFMT` などを「対応形式の候補」として区別し、ホストが使う形式を選んで応答のレコードを作る(`negotiate()`。玉型・サグ・穴あけの基準・文字コード。使える形式が無ければ `STATUS` 17 と修飾ビット)
- プリセットパケット(表 A.5-A.23)の構成と、レコードの不足の確認(`missingPresetRecords()`。`{ all: true }` で必須の印の無いものも含める。附属書 A.3)。自動フォーマット初期化のラベル一覧の不足の確認(`missingRecords()`)
- パケットの組み立てと分解、CRC-16 の計算と検証、レコード順序の確認(ファイルなら `REQ=FIL` などの決まりも確認)
- 座標への変換、左右反転、デバイスが求める点数と向きへの変換(`resampleTrace()`)、HBOX・VBOX・周長の計算、データセットの書き出し(形式 1 は 1 行 80 文字以内に分割)
- 玉型の中心と大きさの確認(`checkSizing()`): 箱の中心のずれ、`HBOX`・`VBOX`・`CIRC` と玉型の食い違い、`BSIZ` と `CSIZ` の両方の指定、片眼の玉型から暗黙に決まる `CSIZ`、`CIRC3D` とサグか `FCRV` から計算した立体の周長(`circumference3D()`)の食い違い
- 基準点のずれのラベル(`FBFCIN` など)を 2 つの基準点と向きに分ける(`referencePoints()`)
- ステータスコード(修飾ビットを含む)、XSTATUS コード、要求種別、機器の種類の日本語の要約

ブラウザでは `vca-records.js`、`vca-parser.js` の順に `<script>` で読み込むと `window.VCA` として使えます。Node.js では `require('./src/vca-parser.js')` で読み込めます(定義表は自動で読み込みます)。定義表が無い場合は、docs/records.md に載せた主なラベルだけを判別します。

### vca-session.js・vca-tcp.js でできること

接続方式に依存しない通信の制御です。送るバイト列は `send` で受け取り、届いたバイト列は `receive()` に渡します。

- 確認応答とタイムアウト(6.1.3): 受け取ったパケットに ACK を返す(CRC が合わなければ NAK)。NAK なら 3 回まで送り直す。CRC の付いたパケットへの応答には、`crc` を指定しなくても CRC を付ける(6.1.2.1)。確認応答 6 秒・パケット 12 秒・文字間 5 秒のタイムアウト(`TIMEOUT` レコードで変更)
- 規格に書かれていない乱れへの対処: ACK が化けて相手が同じパケットを送り直してきたら、2 回は処理しない。ACK より先に相手のパケットが届いたら取り置く。順序が崩れたら `STATUS=12`(同期ずれ、表 A.24)を送って中止する。切断されたら待ちをすぐ `closed` で失敗させる。受信中のパケットが上限(既定 1 MiB、`maxPacket`)を超えたら読み捨てて NAK を返し、`GS` が抜けても次の `FS` で読み直す。扱いと理由は [docs/conformance.md](docs/conformance.md#規格に書かれていない場面の扱い)
- デバイス側(`createDevice()`): 初期化(自動フォーマット・プリセット)、アップロード(TRC・INS・UPL・CMD)、ダウンロード(EDG・GEN・TIM・LNF・要求 ID など)、通知(INF・MNT)。応答の `JOB` が要求と同じかを確かめ、セッションを 1 つずつ進める。TCP では接続後 3 秒待つ。初期化の結果の `warnings` で、規格の推奨との食い違い(データに `DEV`・`VEN`・`MODEL` が無い、ラベル一覧に `R` やインターフェイスレコードがある)と、`ACT` を送ったのにホストが返さないことを知らせる
- ホスト側(`createHost()`): 要求を待ち、種類に合わせて応答する。初期化では要求 ID を割り当て、形式を取り決める(`negotiate()`)。知らない要求 ID には `STATUS=5`、REQ の無いパケットには `ANS=ERR` と `STATUS=18`、応答を作る関数が例外を投げたら `STATUS=8`(ホストの内部エラー)と説明文を返す。対応する要求種別は `requestTypes` で宣言できる。初期化に `ACT` が来たら、`actions` で宣言した操作を `ACT` で返す(7.6.3)。`DRLFMT` を取り決めた要求 ID には、廃止された `DRILL` を送らない(5.5.1.5)
- TCP・UDP(`vca-tcp.js`、Node.js のみ): ローカル接続(デバイスが 50000 で待つ)、リモート接続(ホストが 33512 で待つ)、オートコネクト(UDP 33511 の `REQ=CON`)。オートコネクトでは、知らせの `IP`・`PORT` の形を確かめ、`IP` が UDP の送り主と同じ相手にだけつなぐ(`allow` でつないでよい相手を決められる。断った理由は `onIgnore` で分かる)

```js
const T = require('./src/vca-tcp.js');

// ホスト: 33512 で待ち、加工機の要求に加工のデータを返す
await T.listenHost(33512, { onRequest: req => ({ records: [['DO', 'B'], ['HBOX', '52.00', '52.00']] }) });

// デバイス: ホストへつなぎ(3 秒待ってから)、ジョブ 1234 のデータを要求する
const device = await T.connectDevice('192.168.1.10', 33512);
const r = await device.request('EDG', { job: '1234' });   // r.response が受け取ったデータ
```

**規格の本文と違う点**: 対応しない要求種別(`CMD`・`LNF` や `requestTypes` に無い種別)と、知らない要求種別には `STATUS=16` を返します。本文 7.6.2・7.7.2 は対応しない要求種別に `STATUS=8` を返すとしていますが、表 A.24 では 8 は「ホストの内部エラー」で、「要求の種類が分からない」は 16 です。このライブラリは番号の意味を定めた表 A.24 に合わせ、本文の 8 は誤記と考えています(推測)。本文どおり 8 にしたいとき、または DCS Host Simulator と同じ 18 にしたいときは、`createHost({ statusCodes: { unsupportedRequest: 8, unknownRequest: 18 } })` のように番号を変えられます。理由の詳細は [docs/conformance.md](docs/conformance.md#対応しない要求種別に返す状態コード8-と-16) にあります。

デバイス側は、0 以外の `STATUS` を番号によらず失敗として扱い(`STATUS=5` なら初期化をやり直す)、結果に番号(`status`)と説明文(`statusText`)を入れて返します。相手のホストが 8・16・18 のどれを返しても同じように動きます。

シリアル接続(RS-232C)の部品はありません。シリアルポートのライブラリの受信を `receive()` に、`send` を書き込みにつなげば同じように使えます。

実際の機器とつながるかは確かめていません。独立した実装との照合として、The Vision Council の DCS Host Simulator(ホスト役)に `createDevice` でつなぎ、初期化・ダウンロード(形式 1・4)・アップロード・TIM・INF などが通ることを確かめています(`tools/sim-check.js`)。照合から対応したことは、Simulator のくせとあわせて [docs/conformance.md](docs/conformance.md#独立した実装との照合dcs-host-simulator) にまとめています。

テストは、ブラウザで `tests/run-tests.html` を開くか、Node.js 18 以上で次のコマンドを実行します。依存パッケージは無いので `npm install` は要りません。GitHub では push のたびに Node.js 18・20・22 で自動実行されます。`samples/` のファイルのテスト(警告が無いこと、左右の向き、どのファイルも同じ形であること)と TCP・UDP のテストは、ファイルやソケットを使うため Node.js でだけ行います。

```bash
npm test
```

どのテストが対応表のどの行(規格の節)を確かめているかは、[docs/conformance-tests.md](docs/conformance-tests.md) で分かります。各テストに確かめる行と確かめ方(正常・異常・境界・規格の例・Simulator)を書いてあり、`npm run trace` がこの一覧を作ります。GitHub Actions は、対応表で ◎ の行に正常系と異常系(または境界値)の両方のテストがあること(理由を書いて例外にした行を除く)、一覧が古くないことを確かめます。

規格の「しなければならない」「してはならない」(義務)、「するのがよい」(推奨)、ほかの言い方で書かれた義務は、文ごとに [docs/requirements.md](docs/requirements.md) に一覧にし、このライブラリが確かめるもの・利用者や装置が守るもの・扱わないものに分けてあります。確かめるものにはテストに番号を書いてあり(`req: [番号]`)、GitHub Actions が、テストの無い文が無いことも確かめます。確かめられるのにまだ確かめていない義務があれば、扱いを「未対応」にして、一覧の末尾にまとめます。

テストが本当に処理を確かめているかは、ミューテーションテストで調べられます。実装の一部(境界値・分岐・規格の数値など。壊し方の一覧は `tools/mutate.js`)を 1 つずつわざと壊してテストを走らせ、壊してもテストが通ってしまうもの(生き残り)を一覧にします。生き残りがあれば、その処理を通る場面をテストが作っていないということです。壊したファイルは毎回元に戻します。数分かかるので、GitHub Actions では動かしていません。一覧に無い壊し方まで検出できる保証ではないので、処理を足したら `tools/mutate.js` にも壊し方を足してください。

```bash
npm run mutate
```

`vca-records.js` に入っているのは、ラベル・データ型の記法・左右の別・単数/複数・廃止と後継・プリセットの構成といった事実だけで、規格の説明文は含めていません。各ラベルの意味は [docs/all-records.md](docs/all-records.md) に日本語で書き起こしています。正確な定義は規格書で確認してください。規格書の表 A.1 で `HBO` となっている行は、本文・プリセット表・例に合わせて `HBOX` として収録しています。同じように、表 A.16 の `INSSGUP` は `INSSGOCUP` として収録し、説明文でだけ廃止とされている `CTHK`・`CKPRHI`・`CKPRVI`・`CKTHK` にも廃止の印を付けています。
